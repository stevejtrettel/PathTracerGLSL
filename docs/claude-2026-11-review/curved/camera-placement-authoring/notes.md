## 0. What the code does today (E³)

- The scene already says which space it is in: `SceneDescription.ambientSpace: { type: 'euclidean' | 'hyperbolic' | 'spherical'; parameters?: { curvature?: number } }` [checked-code src/compiler/types.ts:24, 43-46]. Only `euclidean` is registered [checked-code src/components/ambient/index.ts:21-23]; the Validator rejects the others [checked-code src/compiler/analyze/Validator.ts:56-57].
- `resolveMeasurement` copies it into `measurement.ambient` with a fallback, `scene.ambientSpace?.type ?? 'euclidean'` [checked-code src/compiler/plan/measurement.ts:23]. That is CF-17. The Analyzer reads it with no fallback [checked-code Analyzer.ts:52].
- Camera pose: `CameraPose { position?: Vec3; target?: Vec3 }` [checked-code types.ts:735-740]. These are the defaults of the reserved, always-live parameters `camera.position` and `camera.target` [checked-code types.ts:815]. If missing, the feature falls back to `[0,0,8]` and `[0,0,0]` [checked-code src/compiler/generate/features/camera.ts:76]. The CPU look-at frame, `cameraBasis`, uses +Y as world up, with +Z as the fallback reference [checked-code src/components/camera/basis.ts:50-55]. It is shipped as `vec3 u_cameraForward/Right/Up`. `u_cameraPosition` passes through as raw vec3 [checked-code camera.ts:112-115].
- Every occupant reads `vec3` frame uniforms and calls `make_ray(u_cameraPosition, normalize(...), wl)`. Pinhole uses `normalize(forward + ndc.x·tanFov·right + ndc.y·tanFov·up)` [checked-code src/components/camera/pinhole/pinhole.glsl:11-17]. Fisheye uses `cos θ·forward + sin θ·(t.x·right + t.y·up)`, then normalize [checked-code fisheye/fisheye.glsl:29-38]. `make_ray` stores its arguments and does nothing else [checked-code src/glsl/core/ray.glsl:7-13].
- Placement: `Transform { position?: Value<Vec3>; rotation?: AxisAngle | Value<Quaternion>; scale?: Value<number> }`, with local→parent = T·R·S [checked-code types.ts:249-254]. Constant transforms fold into primitive parameters through `classifyPlacement` [checked-code Planner.ts:241-270]. Driven transforms become two vec4 uniforms (q = inverse quaternion, ts = (−Rᵀt, s)) [checked-code Planner.ts:764-866; src/glsl/core/placement.glsl:3-41]. The generator emits Euclidean tiers: identity, translation, mat3 rigid, and similarity [checked-code src/compiler/generate/features/intersection.ts:601-660]. The helper signatures are hard-coded vec3 [checked-code intersection.ts:418-421].
- fable-transforms §1 already names the seam: "a leaf's placement is an element of the ambient space's structure group … H³ … an SO(3,1) element with distance_scale ≡ 1, still a 4×4 matrix" [checked-code docs/fable-transforms.md:34-42]. §6.1 adds that the 2-vec4 ABI "does not privilege Euclid" [checked-code fable-transforms.md:312-315].
- OrbitControls holds (distance, azimuth, elevation, target). Its position is `target + d·(cos el sin az, sin el, cos el cos az)` [checked-code src/app/extensions/OrbitControls.ts:220-225]. It writes both parameters in one batch [checked-code OrbitControls.ts:216].
- KeyboardControls keeps a private R³ Frame. A move is `position += worldDir·dist` [checked-code KeyboardControls.ts:271-277], and it writes `target = position + 5·forward` [checked-code KeyboardControls.ts:289-296]. Roll was removed because the pose has no roll [checked-code KeyboardControls.ts:284-286].
- `flattenGroups` composes with `similarityCompose`, which is Euclidean [checked-code src/authoring/flatten.ts:77, 90, 118]. It has no space argument.
- In thurston-rebuild, Position = {boost: Isometry (mat4), quaternion facing} [checked-code thurston-rebuild/src/core/geometry/Position.js:18-30]. `flow` right-multiplies by `flowFromOrigin` [Position.js:188-193]. A camera ray is `applyPosition(p, v) = applyIsometry(boost, applyFacing(facing, v))` [checked-code core/geometry/shaders/commons2.glsl:51-65]. The H³ `makeTranslationFromDir` is `I + sinh t·M + (cosh t − 1)·M²` [checked-code geometries/hyp/geometry/Isometry.js:112-140]. `reduceError` runs hyperbolic Gram–Schmidt after every multiply [Isometry.js:21-61].

## 1. One authoring convention for points: exponential coordinates at the origin

**Proposal.** In every space, an authored `Vec3` that names a point means exp_o(v): the point reached by walking |v| from the origin in direction v/|v|, in the origin's reference frame. This covers camera position and target, `transform.position`, and light positions. In E³, exp_o(v) = v, so every existing scene keeps its meaning and nothing in the Euclidean code changes [math].
- H³: exp_o(v) = (sinh|v| v̂, cosh|v|). S³: (sin|v| v̂, cos|v|). The round trip log_o(exp_o(v)) = v holds to 1e-15 [checked-num checks.ts].
- S³: the chart covers |v| ≤ π. Vectors with |v| > π wrap around and are not an error, but two different vectors can name the same point. A Validator check that compares points (such as "position ≠ target") must therefore compare the points P, not the vectors v [math]. The current check compares Euclidean vectors [checked-code Validator.ts:845-848].
- The alternatives were hyperboloid 4-tuples, the Poincaré ball and Klein coordinates. Each adds a second spelling, and none of them reduces to today's E³ meaning. Exponential coordinates add the fewest parts [math; thought-through-not-checked against authoring ergonomics].
- **H²×R:** exp_o(v) is still well defined: (exp_{H²}(v_x, v_z), height v_y), if +Y is the R factor to match today's +Y-up convention [checked-code basis.ts:52; OrbitControls.ts:222]. Thurston stores the vertical in `.w` [checked-code survey/thurston-port.md:195-196], so the axis must be named deliberately.

## 2. Placements

**Authored.** Keep the type `Transform { position, rotation, scale }`. In a curved space it means g = T(position)·R(rotation), where T(v) is the transvection along the geodesic from o to exp_o(v), and R fixes o (block-diag(R₃, 1)). This is T·R·S with S removed, so in E³ it is today's similarity with s = 1 [math]. A rotation turns the object about its own center, with axes in the frame carried from the origin by T(position).
- `scale` ≠ 1, or any `{param}` scale, is a Validator error in H³/S³: there is no similarity, and size belongs in the primitive's length parameters. The rule is one predicate, the space type [math].
- Every isometry splits uniquely as T(p)·R (Cartan decomposition), except in S³ when g(o) = −o. So composition stays closed. Composing two (T,R) placements, decomposing the result and rebuilding it gives a relative error of 9e-12 in H³ and 2e-15 in S³ [checked-num checks.ts]. A future `flattenGroups(tree, space)` can therefore keep the `Similarity` record, with `scale` = 1 and `translation` read as exp coordinates.
- A point row in a primitive's parameters, such as a sphere's `center`, can't fold in a curved space, because the curved primitives sit canonically at the origin. Two options: (a) fold it into the placement as a pre-translation, g·T(center). E³ already does this on the retained-frame SDF path [checked-code Planner.ts:868-885 comment]. (b) Reject a nonzero point row. Option (a) is friendlier to authors; option (b) is one rule. [thought-through-not-checked]

**Stored and uploaded.** No folding in a curved space. Every object gets a placement:
- a constant transform becomes one baked `mat4` literal, Ginv = g⁻¹ (world→local);
- a driven transform becomes one `mat4` uniform `u_object<i>Placement` whose compute closure builds Ginv in fp64.

Helper bodies: `placement_rigid(Ginv, x) = Ginv·x`, `placement_dir(Ginv, d) = Ginv·d`, and `placement_normal(Ginv, n) = J·((J·n)·Ginv)`, a row-vector product that needs no second matrix. Here J = diag(1,1,1,−1) in H³ and I in S³. The formula holds to 2e-14 [checked-num checks4.ts]. The inverse is exact and needs no numerical inversion: g⁻¹ = J gᵀ J in H³ and gᵀ in S³ [checked-num checks4.ts, checks.ts].
- Compute T(v) from v with the generator form I + sh(d)·M + σ(…)·M² (thurston's formula), not from P with 1/(1+w). Both agree to 1e-15, but the P-form is singular at the S³ antipode: its isometry error is 3.6e-4 at π−1e-6, while the v-form is exact at |v| = π [checked-num checks.ts, checks5.ts].
- Why mat4 rather than the 8-float (q, P) payload that fable-transforms §6.1 anticipates: either way the call sites must change, because a curved transvection acts on directions and normals too, so `placement_dir` and `placement_normal` need the translation part. The vec3 signatures [checked-code intersection.ts:418-421] cannot be kept. A mat4 is one multiply and one baked literal, and it is the same object a quotient's deck transformation will be. Its cost is 4 uniform vectors per driven object instead of 2, which does not matter in the instancing-free subset. [thought-through-not-checked on GPU]
- **H²×R:** isometries are an SO(2,1) block on the H² part, a shift and an optional flip in height. A rotation is an isometry only about the vertical axis, so other axes are a Validator error. The payload becomes mat3 + shift (thurston uses mat4 + float [checked-code survey/thurston-port.md:187]). So the payload shape must be a per-space fact, not a global one.

**Sliders.** `buildDrivenPlacement`'s field readers (position vec3, quaternion or axis-angle, scale) can be reused as they are [checked-code Planner.ts:773-850]. Only the last lowering step changes: `rigidInverse` → (q, ts) in E³, unchanged; `Ginv` mat4 in curved spaces. A position slider moves the object in exp coordinates.

**Keeping E³ untouched.** The curved path is one branch in the Planner's object loop and one emission arm in the intersection feature, keyed on the scene's space. The Euclidean fold, tiers and helpers do not change. Gate: `npm run digest` compare plus `npm run frames compare` on the E³ suite.

## 3. Camera

**Authored and stored.** Keep `CameraPose { position, target }` as Vec3 in exponential coordinates, and keep the reserved parameters `camera.position` and `camera.target` unchanged in type. The App contract does not change.

**Uploaded.** In curved programs the four camera uniforms keep their names and become `vec4`: P, F, R, U, an orthonormal tangent frame at P under the space's form. They are the columns of the camera isometry. Each is a compute closure over the two pose parameters, memoized as `basisFor` already is [checked-code camera.ts:86-103]. Uploading frame vectors rather than an isometry also works in H²×R, where the isotropy group is too small to map the origin frame onto an arbitrary frame [math].

**The up rule.** This is the one real design choice. In E³, world-up is parallel, so there is only one rule. In a curved space, the "up" carried from somewhere depends on the path it is carried along (holonomy). There are two candidates, and both give orthonormal frames to round-off [checked-num checks.ts]:
- **Origin-centered:** G = T(P)·R₀, where R₀ is today's E³ look-at at o, applied to log_o(T(P)⁻¹·target). Simplest, and independent of how far away the target is. But when you orbit a target that is not at the origin, the horizon rolls: up to 54° (H³, target 3 from o, orbit radius 2) and 11° (S³, target 1.2, radius 0.8) [checked-num checks.ts].
- **Target-centered:** pull back by T(target), look at o from P′ = T(target)⁻¹P using today's E³ rule, then push forward with G = T(target)·T(P′)·R₀. An orbit at fixed elevation is then exactly a rotation of the camera about the target's vertical geodesic (relative error 3e-13 in H³ and 8e-16 in S³; the origin-centered rule fails this check at O(1)) [checked-num checks2.ts]. This is what "orbit = rotate about the target" means. It has two drawbacks:
  1. The roll depends on how far ahead the target is. KeyboardControls puts the target at an arbitrary 5 units ahead [checked-code KeyboardControls.ts:292]. Fix: in a curved space, keep the current dist(P, T) instead of 5 (5 > π in S³ anyway).
  2. The composed product is badly conditioned in H³: frame orthonormality error is 1e-8 at camera distance 6 and 8e-5 at 8. A Gram–Schmidt at P = exp_o(position) brings it back to the origin-centered level (4.7e-10 at d = 8) [checked-num checks3.ts].
- A third option avoids the rule altogether: store the pose as an isometry, as thurston's Position does, so that orbit is G ← T_T·R·T_T⁻¹·G and keyboard is G ← G·local. It changes the reserved parameters and both controls, which is more machinery in an App that is still open for redesign. [thought-through-not-checked]
- **H²×R:** the vertical field is parallel, so "up = vertical" is a global rule, as in E³, and the question goes away [math].

**Pixel to ray.** Pinhole: d = (F + a·R + b·U)/√(1+a²+b²), with a = ndc.x·tanFov and b = ndc.y·tanFov. Fisheye: d = cos θ·F + sin θ·(t.x·R + t.y·U), which is unit with no normalize. Both are unit tangent vectors at P under the form to round-off [checked-num checks.ts]. The ray is `make_ray(P, d)`. So the occupant formulas stay the same, with vec4 in place of vec3. The only change is the normalization. `normalize()` is correct in S³, because the Euclidean R⁴ norm of a tangent vector is its metric norm, but it is wrong in H³ [math].

Simplest shared source: write pinhole.glsl and fisheye.glsl against `Point` and `Direction`, and replace `normalize(dir)` with `ambient_normalize(dir, u_cameraPosition)`. That is a new seam function; the Euclidean body is literally `normalize(v)`, best as a preprocessor alias so the post-preprocessing E³ tokens are identical. The E³ shader text changes in these two files only, so the digest will differ there. The E³ pictures should be bit-identical; prove that with `npm run frames compare` [thought-through-not-checked]. The alternative is a second GLSL file per space on the descriptor. It leaves E³ text untouched, but it duplicates the formula, against "one answer per fact".
- Equirect and cylindrical would generalize the same way, since they only combine frame vectors [checked-code equirect.glsl:24-27; cylindrical.glsl:26-27]. Orthographic (a film-plane origin offset) and thin lens (a focus plane, a lens offset) need real geodesic definitions. All four stay compile errors in the subset.

**Who implements what.** Add one fact per camera descriptor, e.g. `spaces: ['euclidean', 'hyperbolic', 'spherical']`. The Validator then rejects a camera type the scene's space does not list, with an error that names both. This follows the descriptor rule ("facts about one model") [checked-code src/components/camera/index.ts:10-13]. Lights and primitives would carry the same field.

## 4. App controls: what they must do, and the CPU math

**Per-space TS module**, about 40 lines each, for example `components/ambient/hyperbolic/hyperbolic.ts` and `spherical/spherical.ts`: `expO(v)`, `logO(P)`, `transvection(v)` (generator form), `inverse(g)` (J gᵀ J or gᵀ). One shared file, written once against that interface: 4×4 multiply and apply, `cameraFrame(position, target)`, `orbitPosition` and `orbitParams`, `fly`, and `placementInverse(position, quat)`. space.ts is a working prototype of all of it. Euclidean keeps `cameraBasis`, `rigidInverse` and the existing controls untouched.
- **Orbit** (rotate about the target): position = log_o(T(target)·exp_o(d·u(az, el))), and the inverse is the reverse. The round trip holds to 7e-11 in H³ and 9e-15 in S³ [checked-num checks.ts]. In E³ this reduces to today's `target + d·u` [math]. S³: clamp d < π, because today's maxDistance is 100 [checked-code OrbitControls.ts:39].
- **Keyboard** (move = flow): the new P is the flow from P along D by dist, using cosh/sinh (or cos/sin) of t. The forward vector is parallel-transported along that move: F′ = F − ⟨F,D⟩D + ⟨F,D⟩D′ [math; the flow formula is checked in checks.ts: flow(P, F, dist(P,T)) reaches T to 8e-7 (H³) and 2e-15 (S³)]. Yaw and pitch rotate F inside the frame at P. Write position = log_o(P′) and target = log_o(flow(P′, F′, look-ahead)).
- The App knows the space through `rendererManager.getScene()` [checked-code App.ts:823]. How that reaches an extension is an App-API detail that belongs to the App redesign.

## 5. The scene-description change

There is nothing to add. `scene.ambientSpace.type` already exists and is required [checked-code types.ts:24]. The taxonomy puts geometry in the scene: "Scene defines (T, E) … geometry" [checked-code docs/fable-strategy-taxonomy.md:39], and the geodesics are part of T. measurement.ts agrees: "Ambient space rides the SCENE" [checked-code measurement.ts:21-22]. One disagreement to flag: the registry header calls ambient a "measurement pick-one family" [checked-code ambient/index.ts:1]. The taxonomy never mentions ambient (grep -i of fable-strategy-taxonomy.md finds nothing).

Changes:
1. Fix CF-17: drop `?.` and `?? 'euclidean'` [checked-code measurement.ts:23].
2. Register the `hyperbolic` and `spherical` occupants. Add `'h2xr'` (name to be decided) to the union later.
3. `parameters.curvature`: I recommend fixing K = ±1, so lengths are in units of the curvature radius, and rejecting the field. That makes it one fewer parameter in every formula. This is an owner question, and the survey asks it too [checked-code survey/findings.md "Reader questions"].
4. In a curved scene the pose should be required, not defaulted. The fallback `[0,0,8]` [checked-code camera.ts:76] wraps in S³ (8 > π) and is far out in H³. That is a "no guesses" item.

## 6. A precision finding to carry into the design

With float32 uploads and a float32 pinhole, the point at t = 1 along a camera ray in H³ is off by 3e-7 at camera distance 0, 2e-4 at 4, 8e-3 at 6 and 1.6 at 8 from the model origin. The error grows like e^{2d}. In S³ it stays at about 1e-7 everywhere [checked-num checks2.ts]. Even float64 frames lose orthonormality near distance 10 to 12 (1e-8 to 2e-6) [checked-num checks3.ts].

Local-frame intersection does not fix this: the camera ray itself already carries the error before any object transform touches it. The usual remedy is camera-relative coordinates: the CPU, in fp64, premultiplies the camera and every placement by G_cam⁻¹. But that makes every placement depend on the camera, so constant placements could no longer be baked. That is real machinery. For v1: keep H³ scenes and the camera within about 4 of the origin, and document the limit. [checked-num for the numbers; the remedy is thought-through-not-checked]
