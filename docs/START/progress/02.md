## Core Architecture Implemented

### **1. Engine Pillar - Complete Modular Foundation**

**ModuleRegistry** (`engine/ModuleRegistry.ts`)
- **Purpose:** Central repository for rendering modules with validation
- **Current:** Stores modules by kind:name, validates exports declarations
- **Phase 2 Feature:** Registration and retrieval working, validation shell in place
- **Future Ready:** Validation system ready for KIND-based prefixing enforcement

**ShaderCompiler** (`engine/ShaderCompiler.ts`)
- **Purpose:** Transforms modules into executable GLSL + handles uniform management
- **Current:** Module concatenation, dependency ordering, uniform parameter mapping
- **Phase 2 Features:**
    - Correct module ordering (ambient → camera → ...)
    - Main function generation for ray visualization
    - Parameter path to uniform name conversion (`camera.position` → `u_camera_position`)
    - Full uniform type handling (float, vec3, mat3, etc.)
- **Architecture:** Uniform management lives here (not in RenderExecutor) - correct pattern

**RenderExecutor** (`engine/RenderExecutor.ts`)
- **Purpose:** Pure WebGL execution - geometry, drawing, pixel readback
- **Current:** Full-screen triangle setup, shader compilation/linking, draw calls
- **Phase 2 Focus:** Stays clean and focused on execution only
- **Architecture:** No uniform management - maintains proper separation of concerns

**Engine** (`engine/Engine.ts`)
- **Purpose:** Top-level orchestration of the three subsystems
- **Current:** State management (ready/running), module loading, parameter updates
- **Phase 2 Features:**
    - Correct parameter flow: `updateParameters()` → `ShaderCompiler.updateUniforms()`
    - Subsystem initialization in dependency order
    - State transitions for safety
- **Future Ready:** Recipe system will build directly on this foundation

---

### **2. App Pillar - Parameter Management**

**ParameterStore** (`app/ParameterStore.ts`)
- **Purpose:** Single source of truth for all renderer state
- **Current:** Parameter storage, change notification, metadata registration, validation
- **Phase 2 Features:**
    - `onChange` callback pattern (core architecture)
    - Path-based parameter storage (`camera.position`, `camera.fov`)
    - Basic validation against metadata (type checking, clamping)
    - Change tracking with old/new values
- **Architecture:** Pure state management - no rendering knowledge

**MinimalApp** (`app/MinimalApp.ts`)
- **Purpose:** Application orchestration and high-level camera control
- **Current:** ParameterStore ↔ Engine wiring, camera mathematics, module loading
- **Phase 2 Features:**
    - Establishes the real parameter flow: `ParameterStore.set()` → `Engine.updateParameters()`
    - Camera math (position/lookAt/FOV → uniforms)
    - Module loading coordination
- **Future Ready:** Will become ResearchApp with recipe management

---

### **3. Modules - First Real Rendering Logic**

**Euclidean Ambient Space** (`objects/ambient/euclidean/euclidean-ambient.ts`)
- **Purpose:** Mathematical foundation for flat 3D space
- **Exports:** `ambient_geodesic`, `ambient_frame`, `ambient_dot`, `ambient_parallel_transport`
- **Architecture:** Pure mathematics, no scene knowledge, enables non-euclidean spaces later
- **Phase 2 Status:** Defines Point/Direction/Frame types, implements euclidean operations

**Pinhole Camera** (`optics/camera/pinhole-camera.ts`)
- **Purpose:** Ray generation from screen coordinates
- **Exports:** `camera_generateRay`
- **Dependencies:** Uses ambient types (Point, Direction, Frame)
- **Phase 2 Features:**
    - Proper field of view mathematics
    - Aspect ratio correction
    - NDC coordinate conversion
    - World space ray generation
- **Architecture:** First module that depends on another module (ambient)

## Key Interfaces and Patterns

### **Parameter Flow Architecture**
```typescript
ParameterStore.set('camera.position', [0, 0, 5])
    ↓
onChange callback fires
    ↓  
Engine.updateParameters(changes: ParameterChanges)
    ↓
ShaderCompiler.updateUniforms(changes)
    ↓
WebGL uniform calls
```

### **Module Composition Pattern**
```typescript
const modules = [euclideanAmbient, pinholeCamera];
ShaderCompiler.compile(modules) → ordered GLSL with:
// ambient functions first
Point ambient_geodesic(Point origin, Direction dir, float t) { ... }

// camera functions second (can call ambient functions)  
Ray camera_generateRay(vec2 pixel, vec2 xi) {
  // Uses ambient types and functions
}
```

### **TYPE System**
```typescript
// Engine pillar
ModuleDescriptor, ModuleKind, ValidationResult

// App pillar  
ParameterMetadata, ParameterChanges, EngineState

// Cross-pillar interfaces established
Engine.updateParameters(changes: ParameterChanges)
```

**✅ Module Composition Works**

- Dependency ordering prevents undefined function errors
- Clean separation: ambient = pure math, camera = ray generation

**✅ Parameter System Scales**

- Type validation and metadata support

**✅ Engine Orchestration Correct**

- Uniform management delegated to correct component (ShaderCompiler)
- State management provides safety guarantees

**✅ WebGL Abstraction Works**
- RenderExecutor hides all WebGL complexity
- Engine provides clean interface to app layer
- Module system generates valid, executable GLSL
