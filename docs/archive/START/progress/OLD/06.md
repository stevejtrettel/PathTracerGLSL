# Modular Parameter-Driven Rendering System
**Phase 6 Architecture Documentation**

## Overview

We've built a modular rendering architecture that separates user-facing parameters from GPU implementation details. The system enables complex graphics effects through composable modules while maintaining clean architectural boundaries and efficient uniform management.

## Core Architecture

### Component Diagram
```
MinimalApp
    ↓ (parameters)
ParameterStore
    ↓ (change events)  
Engine
    ↓ (orchestration)
┌─────────────┬─────────────────┬──────────────┐
│ModuleRegistry│  ShaderCompiler │RenderExecutor│
└─────────────┴─────────────────┴──────────────┘
                    ↓ (WebGL)
                   GPU
```

### Data Flow
1. **User interaction** → MinimalApp sets semantic parameters
2. **Parameter changes** → ParameterStore batches and notifies
3. **Change propagation** → Engine forwards to ShaderCompiler
4. **Uniform binding execution** → Modules transform parameters to GPU uniforms
5. **Frame rendering** → Engine updates time, calls render pipeline

## Key Design Decisions

### Dual-Path Uniform System
**Engine uniforms** (time, resolution, frame count) are set directly each frame for efficiency.
**Parameter uniforms** flow through the binding system for complex transformations.

This hybrid approach optimizes for the common case while supporting complex parameter-to-uniform relationships.

### Module-Declared Uniform Bindings
Modules explicitly declare how they consume global parameters:

```typescript
uniformBindings: [
  {
    uniform: 'u_camera_tan_fov',
    parameters: ['camera.fov'],
    compute: (params) => Math.tan(params['camera.fov'] * Math.PI / 180 / 2)
  }
]
```

Benefits:
- **Self-contained modules** - each handles its own GPU transformation logic
- **Parameter sharing** - multiple modules can bind to the same parameter
- **Complex transformations** - multi-parameter computations (camera frame matrices)
- **Future generation** - WorldCompiler can generate bindings alongside GLSL

### Semantic Parameter Interface
The app layer works with user-meaningful parameters:
- `camera.fov: 60` (degrees, not radians)
- `light.intensity: 200` (user scale, not physically-based units)
- `camera.target: [0,0,0]` (look-at point, not transformation matrices)

Modules handle the conversion to GPU-appropriate representations.

## Component Details

### ParameterStore
**Responsibilities:**
- Store parameter values with dot-notation paths
- Batch updates for atomic changes
- Change notification with source tracking
- Simple validation and clamping

**Key features:**
- `batch()` method prevents multiple onChange events
- Source tracking ('user', 'engine', 'session') for filtering
- Shallow equality checks avoid unnecessary updates

### Engine
**Responsibilities:**
- Orchestrate subsystems (registry, compiler, executor)
- Track engine state (time, frame count)
- Update engine uniforms each frame
- Forward parameter changes to ShaderCompiler

**Performance characteristics:**
- Engine uniforms updated directly (efficient)
- Parameter changes trigger selective binding updates
- Single render call per frame

### ShaderCompiler
**Responsibilities:**
- Concatenate modules into complete GLSL shader
- Build uniform binding mappings from module declarations
- Execute bindings when parameters change
- Manage uniform locations and GPU updates

**Binding execution:**
1. Find bindings affected by parameter changes
2. Gather current parameter values for each binding
3. Execute binding compute functions
4. Update corresponding GPU uniforms

### Module System
**Module types:** ambient (geometry), scene, lighting, camera, interaction, transport

**Module contract:**
- GLSL fragments (uniforms, constants, functions)
- Uniform bindings (parameter consumption)
- Exports (available functions)
- KIND-based function prefixing

**Example module structure:**
```typescript
const pinholeCamera: ModuleDescriptor = {
  id: { kind: 'camera', name: 'pinhole', version: '1.0.0' },
  fragment: {
    uniforms: `uniform vec3 u_camera_position;`,
    functions: `Ray camera_generateRay(vec2 pixel, vec2 xi) { ... }`
  },
  uniformBindings: [
    {
      uniform: 'u_camera_position',
      parameters: ['camera.position'],
      compute: (params) => params['camera.position']
    }
  ]
};
```

## Current Capabilities

### Direct Lighting Pipeline
- Point light sources with position and intensity control
- Lambert shading with cosine falloff
- Shadow ray testing for occlusion
- Physical light attenuation (inverse square)

### Camera System
- Pinhole camera with look-at controls
- Field of view in user-friendly degrees
- Automatic camera frame matrix generation
- Aspect ratio correction

### Scene Rendering
- SDF-based sphere intersection
- Material property lookup
- Optimized shadow ray queries (`scene_intersect_any`)

### Animation System
- Engine time tracking synchronized with render frames
- Parameter-based animation (light orbiting)
- Continuous rendering loop for real-time updates

### Parameter Management
- Semantic parameter names (`camera.fov`, `light.intensity`)
- Batch parameter updates
- Parameter persistence and session management

## Working Example

Current system renders:
- Sphere with Lambert shading showing light/dark sides
- Point light orbiting around the sphere
- Shadows where light is occluded
- Dynamic lighting that updates in real-time
- Proper camera controls and field of view

**Parameters in use:**
```typescript
'camera.position': [0, 0, 10]
'camera.target': [0, 0, 0]  
'camera.fov': 60
'light.position': [animated]
'light.color': [1.0, 1.0, 1.0]

```

## Performance Characteristics

### Efficient Uniform Updates
- Engine uniforms: 3 direct GPU updates per frame
- Parameter uniforms: Only updated when parameters change
- Binding execution: Only affected bindings re-executed

### Minimal GPU State Changes
- Single shader program compilation at startup
- Uniform updates without program switching
- Optimized shadow ray queries

### Memory Usage
- Static module compilation (no runtime GLSL generation)
- Parameter cache for multi-parameter bindings
- Efficient uniform location caching

## Extensibility Points

### New Module Types
The architecture supports additional module kinds:
- **Film modules** - accumulation strategies
- **Developer modules** - tone mapping
- **Material modules** - BRDF implementations

### Complex Parameter Relationships
Uniform bindings support:
- Multi-parameter computations (camera matrices)
- Parameter sharing across modules
- Time-based animations
- Conditional logic in compute functions

### Generated Modules
The WorldCompiler will generate:
- Scene modules from scene descriptions
- Lighting modules from light definitions
- Material modules from material graphs
- Corresponding uniform bindings

### Future Lighting
Current point light extends to:
- Area lights (rectangular, disk, sphere)
- Environment mapping (HDRI backgrounds)
- Emissive geometry
- Multiple light sources

## Key Architectural Validations

### Separation of Concerns
- **App layer**: User semantics and interaction
- **Parameter layer**: State management and change tracking
- **Module layer**: GPU transformation and rendering logic
- **Engine layer**: System orchestration and optimization

### Testability
- Pure functions in uniform bindings
- Deterministic parameter transformations
- Isolated module compilation
- Predictable rendering pipeline

### Maintainability
- Clear module contracts and interfaces
- Minimal interdependencies between components
- Explicit parameter dependencies in bindings
- Consistent naming and organization

The current system successfully demonstrates physically-based direct lighting with a clean parameter-driven architecture that scales to complex rendering techniques while maintaining performance and modularity.
