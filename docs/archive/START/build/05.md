# Phase 5: First Parameters

## Goals and Purpose

Phase 5 introduces centralized state management through the ParameterStore, establishing the pattern for how all renderer configuration flows through the system. We're solving a fundamental problem: how do we manage the dozens of parameters that control rendering (camera position, material properties, light intensity) in a way that's predictable, debuggable, and extensible?

The key architectural principle being tested is that all state flows through a single store, with changes propagated through a reactive onChange handler. This unidirectional data flow makes the system predictable - parameters change in the store, the store notifies listeners, listeners update uniforms. There's no confusion about where state lives or how changes propagate.

## What We're Building

### The Parameter System Architecture

**ParameterStore as Single Source of Truth** - The ParameterStore becomes the authoritative location for all renderer state. When we want to know where the camera is, we ask the store. When we want to move the camera, we tell the store. The store is the only place that holds parameter values, eliminating synchronization problems between multiple state locations.

**Reactive Update Pattern** - We're establishing the onChange pattern where the store notifies interested parties when parameters change. This reactive approach means components don't poll for changes - they're told when something they care about has changed. For Phase 5, we have just one listener (MinimalApp), but the pattern scales to many observers.

**Direct Uniform Binding** - The connection from parameters to GPU uniforms is direct and explicit. When a parameter changes, we immediately update the corresponding uniform. There's no batching or deferred updates yet - we're establishing the simplest possible flow that maintains correctness.

### Architectural Patterns Established

This phase establishes several critical patterns:

1. **Unidirectional Data Flow** - Parameters flow from store → uniforms → GPU
2. **Change Notification** - Store emits events, doesn't know about consumers
3. **Dot-Notation Paths** - Parameters use hierarchical naming (camera.position)
4. **Type-Agnostic Storage** - Store holds any JSON-serializable value

### What Changes After Phase 5

Before Phase 5: Camera position and FOV are hardcoded or set through ad-hoc methods.

After Phase 5:
- All camera configuration flows through ParameterStore
- Changes to parameters automatically update GPU uniforms
- We can modify camera position/FOV and immediately see results
- The foundation for complex parameter management is in place

Being able to move the camera by setting `store.set('camera.position', [0, 0, 5])` proves our state management works correctly and updates propagate to the GPU.

## Implementation Plan

### File Structure Overview

We're adding the parameter management layer:

1. **Parameter System**
    - `app/parameter-store.ts` - The store implementation
    - `app/types.ts` - Type definitions for parameters

2. **App Integration**
    - Extend MinimalApp to use ParameterStore
    - Add parameter-to-uniform mapping

3. **Uniform Management**
    - Extend Engine to handle uniform updates more systematically

### Implementation Order

Building incrementally to verify each part:

1. **Create ParameterStore class** - Basic get/set functionality
2. **Add change notification** - onChange callback pattern
3. **Wire to MinimalApp** - Connect store to app
4. **Map parameters to uniforms** - Define the parameter→uniform relationship
5. **Test with camera movement** - Verify the flow works end-to-end
6. **Add FOV control** - Second parameter to test pattern generalizes

This order lets us test state management before adding complexity.

## Success Criteria

Phase 5 is complete when:
- Setting camera.position moves the viewpoint
- Setting camera.fov changes field of view
- Changes apply immediately (reactive updates work)
- Batch updates result in single render
- The sphere appears from different viewpoints as we move camera
- Parameter flow is traceable from store to GPU

The ability to move the camera proves:
- ParameterStore correctly manages state
- onChange notifications work
- Parameter-to-uniform mapping is correct

## Key Architectural Validations

This phase validates critical architectural patterns:

1. **Centralized State Works** - Single source of truth eliminates synchronization bugs
2. **Reactive Updates Scale** - onChange pattern will handle complex scenarios
3. **Dot-Notation Organizes** - Hierarchical paths organize many parameters
4. **Type-Agnostic Storage** - Store handles vec3, float, etc. uniformly

The visual feedback is simple - the camera moves - but we've established the state management pattern that will eventually handle hundreds of parameters across materials, lights, camera, and more. The unidirectional data flow from store to GPU creates a predictable, debuggable system where state changes are traceable and effects are immediate.
