Yeah, you’re reading it right, but let’s make it much more concrete and explicit.

Think of the **Material module** as “the thing that, given a `mat_id` and a point `p`, hands Transport+Interaction a *fully populated* `MaterialProperties` struct.”

---

## 1. What is the Material module’s *runtime* contract?

At the GLSL level, the **minimum contract** looks like:

```glsl
// 1. Data type
struct MaterialProperties {
    // Surface
    vec3  base_color;
    float roughness;
    float metallic;
    float ior;
    float specular;

    // Volume
    vec3  sigma_s;
    vec3  sigma_a;
    float phase_g;

    // Local emission
    vec3  emission;
    float emission_strength;

    // Flags / metadata (bitfield or enum-like)
    int   flags;
};

// 2. Main query
MaterialProperties material_get_properties(int mat_id, vec3 p);

// 3. Classification helpers
bool material_has_volume(int mat_id);
bool material_is_emissive(int mat_id);

// (Optional extras)
// bool material_is_delta(int mat_id);
// bool material_is_dielectric(int mat_id);
// ...etc.
```

Plus some **compile-time IDs**:

```glsl
// material IDs – generated by the compiler
#define MAT_AIR    0
#define MAT_GLASS  1
#define MAT_SMOKE  2
// ...
```

That’s really it. From the rest of the system’s point of view:

* Transport calls `material_get_properties(mat_id, p)` to get a `MaterialProperties` value.
* Transport/Interaction call `material_has_volume(mat_id)` or `material_is_emissive(mat_id)` when they need to classify what they’re dealing with.
* The **material module owns the mapping** from `mat_id` to all those fields + flags.

Everything else (how we build those functions, what uniforms they use) is work done by the **MaterialCompiler** on the TS side.

---

## 2. How is it “assembled” from TS?

Yes: we make a **big list of materials in TS**, and the MaterialCompiler emits:

* `#define` constants for material IDs,
* uniforms (`u_material_...`) based on parameter references,
* `material_get_properties` as a big `if/else` or `switch` on `mat_id`,
* `material_has_volume`, `material_is_emissive` similarly.

Let’s walk through that concretely.

### 2.1 TS-side description (author writes this)

Something like:

```ts
type Vec3 = [number, number, number];

type MaterialPropertyValue<T> =
  | T
  | { param: string };

interface MaterialDescription {
  surface?: {
    baseColor?: MaterialPropertyValue<Vec3>;
    roughness?: MaterialPropertyValue<number>;
    metallic?:  MaterialPropertyValue<number>;
    ior?:       MaterialPropertyValue<number>;
  };
  volume?: {
    sigmaS?: MaterialPropertyValue<Vec3>;
    sigmaA?: MaterialPropertyValue<Vec3>;
    phaseG?: MaterialPropertyValue<number>;
  };
  emission?: {
    emission?:         MaterialPropertyValue<Vec3>;
    emissionStrength?: MaterialPropertyValue<number>;
  };
  flags?: {
    hasVolume?: boolean;
    isEmissive?: boolean;
  };
}

interface MaterialSystemDescription {
  materials: Map<string, MaterialDescription>;
  parameters?: Record<string, ParameterMetadata>;
}
```

Example “world materials”:

```ts
const materials = new Map<string, MaterialDescription>([
  ['air', {
    surface: { baseColor: [1,1,1], roughness: 0.0 },
    flags: { hasVolume: false, isEmissive: false },
  }],
  ['redDiffuse', {
    surface: {
      baseColor: { param: 'mat.red.baseColor' },
      roughness: { param: 'mat.red.roughness' },
    },
    flags: { hasVolume: false, isEmissive: false },
  }],
  ['smoke', {
    volume: {
      sigmaS: { param: 'mat.smoke.sigmaS' },
      sigmaA: { param: 'mat.smoke.sigmaA' },
      phaseG: 0.0,
    },
    flags: { hasVolume: true, isEmissive: false },
  }],
]);

const parameters = {
  'mat.red.baseColor': { type: 'color', default: [1, 0.2, 0.2] },
  'mat.red.roughness': { type: 'float', default: 0.5 },
  'mat.smoke.sigmaS':  { type: 'vec3',  default: [0.1, 0.1, 0.1] },
  'mat.smoke.sigmaA':  { type: 'vec3',  default: [0.01, 0.01, 0.01] },
};
```

### 2.2 MaterialCompiler: step-by-step

Given that `MaterialSystemDescription`, the compiler does:

#### (1) Assign numeric material IDs

Walk `materials` in some order:

```ts
// internal
const materialIds = new Map<string, number>();
let nextId = 0;
for (const name of materials.keys()) {
  materialIds.set(name, nextId++);
}
```

Then emit:

```glsl
#define MAT_AIR        0
#define MAT_REDDIFFUSE 1
#define MAT_SMOKE      2
```

*(Names normalized to constants; this is exactly like what you already do for materials/lights in other parts of the system.)*

#### (2) Analyze parameter usage

Look at each `MaterialDescription` and its nested fields:

* For `'redDiffuse'`:

    * `surface.baseColor = { param: 'mat.red.baseColor' }` → usage: `'mat.red.baseColor' → vec3`
    * `surface.roughness = { param: 'mat.red.roughness' }` → usage: `'mat.red.roughness' → float`
* For `'smoke'`:

    * `volume.sigmaS = { param: 'mat.smoke.sigmaS' }` → usage: `'mat.smoke.sigmaS' → vec3`
    * `volume.sigmaA = { param: 'mat.smoke.sigmaA' }` → usage: `'mat.smoke.sigmaA' → vec3`

Build a map:

```text
mat.red.baseColor  → vec3
mat.red.roughness  → float
mat.smoke.sigmaS   → vec3
mat.smoke.sigmaA   → vec3
```

#### (3) Emit uniforms

For each param path, generate a uniform name:

```ts
function paramToMaterialUniform(path: string) {
  return 'u_material_' + path.replace(/\./g, '_');
}
```

So:

* `'mat.red.baseColor'` → `u_material_mat_red_baseColor`
* `'mat.red.roughness'` → `u_material_mat_red_roughness`
* etc.

And emit:

```glsl
uniform vec3  u_material_mat_red_baseColor;
uniform float u_material_mat_red_roughness;
uniform vec3  u_material_mat_smoke_sigmaS;
uniform vec3  u_material_mat_smoke_sigmaA;
```

#### (4) Emit `MaterialProperties` struct

This is mostly fixed:

```glsl
struct MaterialProperties {
    vec3  base_color;
    float roughness;
    float metallic;
    float ior;
    float specular;

    vec3  sigma_s;
    vec3  sigma_a;
    float phase_g;

    vec3  emission;
    float emission_strength;

    int   flags;
};
```

#### (5) Emit `material_get_properties`

This is the “big function assembled from all materials”:

```glsl
MaterialProperties material_get_properties(int mat_id, vec3 p) {
    MaterialProperties mp;

    // sensible defaults
    mp.base_color        = vec3(1.0);
    mp.roughness         = 0.5;
    mp.metallic          = 0.0;
    mp.ior               = 1.5;
    mp.specular          = 0.0;

    mp.sigma_s           = vec3(0.0);
    mp.sigma_a           = vec3(0.0);
    mp.phase_g           = 0.0;

    mp.emission          = vec3(0.0);
    mp.emission_strength = 0.0;

    mp.flags             = 0;

    if (mat_id == MAT_AIR) {
        // from 'air' description
        mp.base_color = vec3(1.0);
        mp.roughness  = 0.0;
        // flags might stay 0

    } else if (mat_id == MAT_REDDIFFUSE) {
        // from 'redDiffuse' description:
        mp.base_color = u_material_mat_red_baseColor;
        mp.roughness  = u_material_mat_red_roughness;
        mp.metallic   = 0.0;
        mp.ior        = 1.5;
        // etc.

    } else if (mat_id == MAT_SMOKE) {
        // from 'smoke'
        mp.sigma_s = u_material_mat_smoke_sigmaS;
        mp.sigma_a = u_material_mat_smoke_sigmaA;
        mp.phase_g = 0.0;
        // plus any surface/emission fields you set
    }

    return mp;
}
```

That’s the “assemble” step: the compiler literally generates these `if/else` blocks by iterating over the map of `materials` and their properties.

If you prefer, it can also generate `switch(mat_id)` with cases; same idea.

#### (6) Emit classification functions

Using `flags` and/or description’s `flags`:

```glsl
// e.g. pack bitflags before codegen:
#define MATERIAL_FLAG_VOLUME   1
#define MATERIAL_FLAG_EMISSIVE 2

bool material_has_volume(int mat_id) {
    if (mat_id == MAT_SMOKE) return true;
    return false;
}

bool material_is_emissive(int mat_id) {
    if (mat_id == MAT_REDEMISSIVEPANEL) return true;
    return false;
}
```

Or you can simply codegen them directly from description’s `flags.hasVolume` / `flags.isEmissive`.

#### (7) Uniform bindings back to JS/TS

For each param path we tracked (`'mat.red.baseColor'`, etc.), we add a binding:

```ts
const uniformBindings: UniformBinding[] = [];

for (const [paramPath, type] of paramUsage) {
  const uniformName = paramToMaterialUniform(paramPath);
  const meta = parameters[paramPath];

  uniformBindings.push({
    uniform: uniformName,
    parameters: [paramPath],
    type, // 'float' | 'vec3'
    compute: (params) => params[paramPath] ?? meta.default,
  });
}
```

Those bindings tell the engine:

* “When you go to render a frame, for uniform `u_material_mat_red_baseColor`, look up `params['mat.red.baseColor']` in the current parameter set, or use its default, and upload that to the GPU.”

---

## 3. TL;DR – answering your questions directly

> what is its contract? what functions must it provide? what glsl must it provide?

**At runtime, the Material module must provide:**

1. A `MaterialProperties` struct definition with the fields Interaction/Transport need.
2. Compile-time material ID defines:

   ```glsl
   #define MAT_SOMETHING 0
   ...
   ```
3. Functions:

   ```glsl
   MaterialProperties material_get_properties(int mat_id, vec3 p);
   bool material_has_volume(int mat_id);
   bool material_is_emissive(int mat_id);
   ```

   (Plus any optional helpers like `material_is_delta`, etc.)

That’s the whole contract.

> Then how is it assembled? we make a big list of materials in TS and then assemble this function material_get_properties from all of them?

Exactly:

* On the TS side, you define a **map of named materials** with `MaterialDescription`s.
* The MaterialCompiler:

    * Assigns each name a `mat_id`,
    * Scans for `{ param: '...' }`,
    * Emits `uniform` declarations,
    * And **codegens** `material_get_properties` as a big `if/else` (or `switch`) that fills a `MaterialProperties` struct based on those descriptions.

Transport and Interaction never see any of that plumbing—they just call:

```glsl
MaterialProperties mp = material_get_properties(hit.material_to, hit.p);
```

and everything else “just works”.
