# Phase 2: First Ray + Minimal App Shell

## Goals and Purpose

Phase 2 introduces our first real rendering modules and establishes the pattern for how modules compose to create images. We're building the mathematical foundation (geometry) and the entry point to the renderer (camera), while also creating the minimal application shell that will orchestrate rendering.

The critical test here is that two independent modules - geometry and camera - can work together through well-defined interfaces. The camera module will use geometry functions to construct rays, proving that our module system supports proper composition. We're also validating that our KIND-based prefixing prevents namespace collisions and makes module boundaries clear in the generated code.

## What We're Building

### First Real Modules

**Euclidean Geometry Module** provides the mathematical foundation for 3D space. This is our first "pure" module - it has no scene knowledge, no rendering concerns, just mathematical operations on points and directions. The geometry module answers questions like "what point do I reach traveling from here in this direction?" and "how do I build an orthonormal frame?". These operations are fundamental to everything else in the renderer.

**Pinhole Camera Module** generates rays from screen coordinates. This is our first module that depends on another - it uses geometry functions to construct rays in world space. The camera establishes the pattern of how screen pixels map to rays, implementing the mathematical model of an ideal pinhole camera. Importantly, it handles antialiasing by accepting a random offset for each pixel.

**MinimalApp Class** creates the thinnest possible orchestration layer. Unlike the raw test harness from Phase 1, MinimalApp represents the beginning of our application architecture. It owns an Engine instance and provides a `render()` method, but at this stage does little more than trigger frame rendering. This shell will grow into our full application, but we're starting with the absolute minimum.

### Architectural Patterns Established

This phase establishes several critical patterns:

1. **Module Composition** - Camera uses Geometry, proving modules can build on each other
2. **PREFIX Safety** - Functions like `geometry_geodesic()` and `camera_generateRay()` can't conflict
3. **Pure vs Stateful Modules** - Geometry is pure math, Camera has uniforms
4. **Random Number Infrastructure** - First use of `next_2d()` for antialiasing

### What Changes After Phase 2

Before Phase 2: We can display a solid color but have no concept of 3D space or viewing.

After Phase 2:
- We can generate rays from any screen position
- Each pixel shows the ray direction as a color (R=X, G=Y, B=Z)
- The mathematical foundation for 3D rendering is in place
- We have a minimal app structure ready to grow

The colored output (a gradient showing ray directions) proves that our camera is correctly generating rays for each pixel and that our modular architecture supports real rendering logic.

## Implementation Plan

### File Structure Overview

We're adding three major components:

1. **Modules directory** - Houses our actual rendering modules
    - `modules/geometry/euclidean.ts` - The geometry implementation
    - `modules/camera/pinhole.ts` - The camera implementation

2. **App layer** - The orchestration above the engine
    - `app/minimal-app.ts` - Simple app shell
    - `app/types.ts` - App-level type definitions

3. **Math infrastructure** - Random number generation
    - `math/random.glsl` - Provides `next_2d()` and friends

### Implementation Order

Building in this sequence ensures testability:

1. **Math infrastructure** - Add random number functions (needed by camera)
2. **Geometry module** - Pure mathematical functions, no dependencies
3. **Test geometry** - Verify functions work correctly in isolation
4. **Camera module** - Depends on geometry being correct
5. **MinimalApp** - Wire everything together
6. **Integration test** - See ray directions on screen

This order means each component can be verified before the next depends on it.

### Main Shader Integration

The main function that ties our modules together will look like:

```glsl
void main() {
  vec2 pixel = gl_FragCoord.xy;
  vec2 xi = next_2d();  // Random offset for antialiasing
  
  Ray ray = camera_generateRay(pixel, xi);
  
  // Visualize ray direction as color
  vec3 color = ray.direction * 0.5 + 0.5;  // Map [-1,1] to [0,1]
  
  gl_FragColor = vec4(color, 1.0);
}
```

This visualization maps ray directions to colors, creating a gradient that proves our camera is working. The center of the screen (looking forward) will be blue (Z=1), while the edges show the spread of the camera's field of view.

## Success Criteria

Phase 2 is complete when:
- The screen shows a gradient of colors representing ray directions
- Camera rays spread according to field of view
- Geometry functions compute correct transformations
- Module prefixing prevents any namespace collisions
- The app can update camera position and FOV
- Random offsets create slight pixel variation (proving antialiasing works)

The gradient we see proves that:
- Modules can successfully use each other's exports
- The camera is generating geometrically correct rays
- Our mathematical foundation is solid
- The app layer can orchestrate module-based rendering

## Key Architectural Validations

This phase validates several architectural decisions:

1. **Module Composition Works** - Camera successfully uses Geometry functions
2. **Prefixing Prevents Conflicts** - No namespace collisions despite multiple modules
3. **Pure Modules Are Reusable** - Geometry has no rendering knowledge yet supports rendering
4. **The App Layer Is Minimal** - Orchestration is separate from implementation

The visual output is simple, but the architecture we're proving is sophisticated. We've shown that independent modules can compose to create images, setting the stage for the complex interactions to come.
