# Phase 4: First Material Property

## Goals and Purpose

Phase 4 establishes the fundamental architectural separation that makes our renderer maintainable and extensible: Scene provides DATA about materials, while Interaction provides BEHAVIOR for how light interacts with those materials. This separation is critical - it means we can change shading models without touching scene description, and we can modify scene content without understanding physics.

We're testing this principle with the simplest possible material property - albedo (base color). The Scene module will say "this sphere is red" (data), while the Interaction module will determine how that redness appears when viewed (behavior). This clean separation enables future complexity where dozens of material properties flow through a consistent interface.

## What We're Building

### The Data/Behavior Split

**Material Properties as Pure Data** - The Scene module extends to provide material information, but critically, it provides only raw values. It says "the albedo is (0.8, 0.2, 0.2)" but makes no decisions about how that color affects appearance. Scene is a database, not a shading system.

**Interaction Module as Physics Engine** - The new Interaction module owns all decisions about light-matter interaction. It receives material properties and viewing geometry, then computes how light behaves. For Phase 4, this is trivial (just return the albedo), but the architecture we're establishing will eventually support complex BRDFs, subsurface scattering, and other phenomena.

**Transport Module as Orchestrator** - We introduce a minimal Transport module that coordinates the rendering process. It traces rays, finds intersections, queries materials, and delegates to Interaction for shading. Transport owns the algorithm but not the physics.

### Architectural Patterns Established

This phase establishes several critical patterns:

1. **Material Properties are Opaque to Scene** - Scene doesn't know how properties will be used
2. **Interaction is Stateless** - Pure functions from geometry and materials to appearance
3. **Transport Orchestrates Without Knowing Physics** - Algorithms separate from equations
4. **Materials Referenced by ID** - Not embedded in geometry

### What Changes After Phase 4

Before Phase 4: We see surface geometry (normals) but no material properties.

After Phase 4:
- Objects have intrinsic colors (albedo)
- The sphere appears as a solid color rather than normal visualization
- Material properties flow from Scene through to final pixels
- The data/behavior separation is proven to work

The solid red sphere we'll see proves that material data can flow from Scene through Transport to Interaction and finally to pixels, all while maintaining clean architectural boundaries.

## Implementation Plan

### File Structure Overview

We're adding two new modules and extending Scene:

1. **Interaction Module**
    - `modules/interaction/simple.ts` - Trivial shading (returns albedo)

2. **Transport Module**
    - `modules/transport/direct.ts` - Single ray, no bounces

3. **Scene Module Extension**
    - Extend to include material properties
    - Add material query functions

### Implementation Order

Building in layers to validate each architectural boundary:

1. **Extend Hit structure** - Add material ID field
2. **Add material properties** - Define albedo-only MaterialProperties
3. **Extend Scene module** - Add `scene_material_properties()`
4. **Create Interaction module** - Implement `interaction_surface_shade()`
5. **Create Transport module** - Orchestrate ray→hit→shade pipeline
6. **Update main shader** - Use Transport instead of direct intersection

This order lets us test that data flows correctly before adding behavior.

## Implementation Sketch

### Extended Hit Structure

```glsl
struct Hit {
  Point p;          // Position of intersection
  vec3 n;           // Surface normal
  float t;          // Distance along ray
  int material_to;  // NEW: Material we're looking at
}
```

The addition of `material_to` establishes that every surface has associated material properties. The naming anticipates future bidirectional needs (glass, volumes) where we'll track materials on both sides of an interface.

### Material Properties Structure

```glsl
struct MaterialProperties {
  vec3 albedo;      // Base color, for now our only property
  // Future: roughness, metallic, emission, etc.
}
```

Starting with just albedo keeps Phase 4 focused on architecture, not complex shading. The structure will grow but the interface pattern is established now.

### Extended Scene Module

```typescript
const sphereWithMaterial: ModuleDescriptor = {
  id: { kind: 'scene', name: 'sphere-albedo', version: '1.0.0' },
  
  fragment: {
    uniforms: `
      // For now, hardcode one material
      const vec3 SPHERE_ALBEDO = vec3(0.8, 0.2, 0.2);  // Red
    `,
    
    functions: `
      bool scene_intersect(Ray ray, out Hit hit) {
        // Same marching as Phase 3
        // But now also set: hit.material_to = 1
        // Returns: true if hit
      }
      
      MaterialProperties scene_material_properties(int mat_id, Point p) {
        // Query material data by ID
        // For Phase 4, ignore p (spatially uniform)
        // Returns: MaterialProperties with just albedo filled
        
        MaterialProperties props;
        if (mat_id == 1) {  // Our sphere
          props.albedo = SPHERE_ALBEDO;
        } else {  // Air/background
          props.albedo = vec3(0.0);
        }
        return props;
      }
    `
  },
  
  exports: ['scene_intersect', 'scene_material_properties']
};
```

The critical point: `scene_material_properties()` returns DATA, not appearance. It doesn't know about viewing angles, lighting, or any other rendering concern. The Point parameter anticipates spatially-varying properties (textures) but isn't used yet.

### Interaction Module

```typescript
const simpleInteraction: ModuleDescriptor = {
  id: { kind: 'interaction', name: 'simple', version: '1.0.0' },
  
  fragment: {
    functions: `
      vec3 interaction_surface_shade(vec3 wi, vec3 wo, Hit hit) {
        // Compute appearance given:
        // wi: incoming light direction (from eye for Phase 4)
        // wo: outgoing light direction (toward eye for Phase 4)  
        // hit: geometric and material information
        
        // Get material data from Scene
        MaterialProperties props = scene_material_properties(
          hit.material_to, hit.p
        );
        
        // For Phase 4: just return albedo
        // No lighting calculation yet
        return props.albedo;
      }
    `
  },
  
  exports: ['interaction_surface_shade']
};
```

Interaction receives geometric context and queries material properties, then computes appearance. The separation is clean: Scene doesn't know this function exists, and Interaction doesn't know how materials are stored.

### Transport Module

```typescript
const directTransport: ModuleDescriptor = {
  id: { kind: 'transport', name: 'direct', version: '1.0.0' },
  
  fragment: {
    functions: `
      vec3 transport_trace(Ray ray) {
        // Orchestrate the rendering pipeline
        // For Phase 4: single ray, no bounces
        
        Hit hit;
        if (!scene_intersect(ray, hit)) {
          // Ray missed everything
          return vec3(0.0);  // Black background
        }
        
        // Compute shading
        // wo: toward camera (negative ray direction)
        // wi: not used yet (will be for lights)
        vec3 wo = -ray.direction;
        vec3 wi = vec3(0.0);  // Placeholder
        
        return interaction_surface_shade(wi, wo, hit);
      }
    `
  },
  
  exports: ['transport_trace']
};
```

Transport knows the ALGORITHM (trace ray, find hit, compute shade) but not the PHYSICS (how materials interact with light). This separation means we can swap shading models without changing the algorithm.

### Updated Main Shader

```glsl
void main() {
  vec2 pixel = gl_FragCoord.xy;
  vec2 xi = next_2d();
  
  Ray ray = camera_generateRay(pixel, xi);
  
  // Use Transport instead of direct intersection
  vec3 color = transport_trace(ray);
  
  gl_FragColor = vec4(color, 1.0);
}
```

The main shader becomes even simpler - it just connects camera rays to the transport pipeline. All rendering logic lives in modules.

## Success Criteria

Phase 4 is complete when:
- The sphere appears as solid red (or whatever albedo we set)
- No normal visualization remains - pure material color
- Changing albedo in Scene changes sphere color
- The data flow works: Scene→Transport→Interaction→Pixel
- Clear separation between data (Scene) and behavior (Interaction)

The solid colored sphere proves:
- Material properties flow correctly through the pipeline
- Scene successfully provides data without knowing its use
- Interaction successfully computes appearance from data
- Transport successfully orchestrates without knowing physics

## Key Architectural Validations

This phase validates the fundamental architecture:

1. **Data/Behavior Separation Works** - Scene and Interaction have distinct responsibilities
2. **Transport Orchestrates Cleanly** - Algorithm separate from physics
3. **Material Properties Flow Correctly** - Data path from Scene to pixels
4. **Modules Compose Without Coupling** - Each module has a clear, limited role

The visual output is trivial - a solid color sphere - but the architecture we've proven is profound. We've established that materials can be pure data, shading can be pure behavior, and transport can orchestrate without understanding either. This separation enables everything from switching between Lambert and Disney BRDF to implementing volumetric rendering, all without architectural changes.
